# 엔딩 링크드 — 파트 구분 설계 (조문 O2O · 내 부고 준비 · 확장)

- 작성일: 2026-11-02
- 상태: 초안 (사용자 결정 5건 대기, 13절)
- 기반: 사용자가 준 「엔딩 링크드」 기획안 + 운영 중인 Part 1 「더나음 장례안내」(`2026-11-02-deonaeum-funeral-guide-design.md`)

표기: **[결정]** 사용자가 정한 것 · **[제안]** Claude가 정한 것 · **[법검토]** 출시 전 전문가 확인 필수 · **[확인 필요]** 만들기 전 사실 확인

## 1. 한 줄 요약

장례 전 과정을 하나로 잇는다. 이미 배포한 **장례 안내(Part 1)** 위에 세 파트를 별도 세션으로 나눠 붙인다.
- **조문 O2O(Part 2):** 빈소별 모바일 페이지
- **내 부고 준비·사전 상속(Part 3):** 본인이 미리 준비
- **확장(Part 4):** 화환·행정 대행·영구 추모관

## 2. 왜 파트를 나누나

| 파트 | 성격 | 서버·개인정보 | Part 1 원칙과의 관계 |
|---|---|---|---|
| 1. 장례 안내 (배포됨) | 공공정보 안내 | 없음 | 기준 |
| 2. 조문 O2O | 상주·조문객 실사용 서비스 | **필요** (방명록, 사진, 연락처) | "개인정보 미수집" 원칙이 깨진다. 별도 개인정보처리방침과 보안이 필요하다 |
| 3. 내 부고 준비 | 본인 기록·계산·가이드 | 가벼운 부분은 불필요, 지정인·자동 부고는 **필요** | 3-A는 Part 1처럼 기기 저장으로 가능하다 |
| 4. 확장 | 결제·제휴·영구 보관 | **필요** + 결제·통신판매 | 사업자 요건이 생긴다 |

- 파트마다 필요한 기술, 법적 요건, 비용이 다르다. 그래서 세션(작업 단위)을 나눈다. **[결정]**
- 공통 원칙은 Part 1에서 그대로 가져온다. 상주에게 도움 최우선, 근거 명시, 제휴 여부로 노출을 바꾸지 않음, 화려하지 않은 "비움" 디자인. **[결정]**

## 3. 공통 설계 원칙 (모든 파트)

- **더나음은 돈을 직접 만지지 않는다. [제안]** 조의금, 화환 대금, 상속 관련 비용이 더나음 계좌를 거치지 않게 한다. 거치면 전자금융업 등록이나 결제대행(PG) 계약 문제가 생긴다. **[법검토]**
- **법률·세무 "연결"은 광고형 정보 제공까지만 한다. [제안]** 변호사법 제34조는 대가를 받고 특정 변호사에게 소개·알선하는 것을 금지한다(위반 시 7년 이하 징역 또는 5천만 원 이하 벌금). 그래서 사건별로 연결하고 수수료를 받는 구조는 만들지 않는다. 무료 공공 상담처를 먼저 안내한다. 대한법률구조공단 132, 국세청 126은 **[확인 필요]**. **[법검토]**
- **"자동 부고"는 사람이 확인해야만 발송한다. [제안]** 임종을 시스템이 판단하지 않는다. 지정인(유언 집행인)이 사망 사실을 확인하고 발송 버튼을 누른다. 잘못된 부고는 되돌릴 수 없는 피해이기 때문이다.
- **법적 효력은 과장하지 않는다. [제안]** 민법이 인정하는 유언은 다섯 방식뿐이다(자필증서, 녹음, 공정증서, 비밀증서, 구수증서). 앱에서 쓴 글, 카톡, 단순 영상은 유언 효력을 인정받기 어렵다. 화면에서 "법적 유언"과 "마음 전하기 메시지"를 분명히 구분한다.
- **민감정보는 최소로 받고 암호화한다.** 재산 목록, 유언 내용, 연락처가 대상이다. 보관 기한과 삭제 방법을 미리 정한다. **[법검토]** 개인정보보호법.

## 4. Part 2 — 조문 O2O "빈소 페이지"

### 4.1 무엇
상주가 빈소 하나당 모바일 페이지를 하나 만든다. 조문객은 빈소의 QR이나 부고 링크로 들어온다. 앱 설치는 필요 없다.

### 4.2 기능과 범위

| 기능 | 1차 (MVP) | 나중 | 비고 |
|---|---|---|---|
| 부고·일정 안내 | 빈소, 발인 일시, 장지 위치, 안내 버스 탑승 정보 | — | Part 1 장례식장·장지 데이터와 연결 |
| 디지털 방명록 | 이름, 관계(선택), 서명(그리기) | 연락처 수집 | 연락처는 필수로 받지 않는다 [제안] |
| 추모 메시지 | 롤링페이퍼형 글, 리본 문구 | 사진 첨부 | 상주가 숨기거나 삭제할 수 있다 (욕설·스팸 대비) |
| 조의금 | **상주가 직접 등록한 계좌번호·카카오페이/토스 송금 링크 표시**, 계좌번호 복사 | 입금 내역 자동 집계 | 자동 집계는 은행·오픈뱅킹 연동이라 별도 자격이 필요하다 **[법검토]**. 1차는 상주가 직접 표시하는 "조의금 메모장" |
| 고인 추억 갤러리 | 상주가 올린 사진·약력 타임라인 | 조문객 업로드(UGC), 영상 | UGC는 상주 승인 후 공개 [제안] |
| 감사 인사 | 상주가 감사 문구를 쓰면 방명록 화면에 표시 | 문자·알림톡 자동 발송 | 자동 발송은 연락처 수집, 발신번호 등록, 비용이 생긴다 |
| 상주 관리 화면 | 방명록·메시지 목록, 엑셀 내보내기 | — | 부의록 수기 작성 대체 |

### 4.3 접근과 보안 [제안]
- **상주 로그인:** 휴대폰 본인확인 대신 "관리 링크 + 4자리 비밀번호"로 시작한다. 본인확인 서비스는 계약과 비용이 든다.
- **빈소 페이지 주소:** 추측할 수 없는 무작위 주소를 쓴다. 검색엔진 노출을 막는다(noindex).
- **보관 기간:** 장례 후 90일이 지나면 자동 비공개, 1년 뒤 삭제한다. 영구 보관을 원하면 Part 4 추모관으로 옮긴다.

### 4.4 기술 [제안]
- Part 1 정적 사이트로는 안 된다. 서버와 DB, 파일 저장소가 필요하다.
- 후보는 Supabase(인증, Postgres, 저장소)나 Firebase다. 둘 다 소규모는 무료이고 유료 전환 기준이 분명하다.
- 화면은 Part 1과 같은 디자인 토큰과 "비움" 방향을 쓴다.
- QR 인쇄물(빈소 거치용 A5 카드)은 PDF로 생성한다.

### 4.5 현장 연계
- 실제 빈소에 QR이 놓이려면 장례식장이나 상조회사의 협조가 필요하다. HN상조 제휴의 자연스러운 접점이다. **[결정 필요]** 13절
- 현장 전광판에 메시지를 송출하는 기능은 장례식장 장비 연동이 필요해 Part 4로 미룬다.

## 5. Part 3 — 내 부고 준비 · 사전 상속

서버가 필요 없는 **3-A**와 서버가 필요한 **3-B**로 나눈다. 3-A는 Part 1 구조 그대로 바로 만들 수 있다. **[제안]**

### 5.1 Part 3-A (기기 저장, 개인정보 미수집 유지)

| 기능 | 내용 | 근거 |
|---|---|---|
| 장례 선호 방식 기록 | 화장/매장, 종교식, 장지 유형, 수의·관 선호, 조문객 범위, 영정 사진 메모 | Part 1의 장례 방식·장지 데이터 재사용 |
| 가족에게 전하기 | 기록을 **PDF로 저장하거나 인쇄**해 가족에게 직접 전달 | 서버에 올리지 않는다 |
| 법정상속분 계산기 | 가족 구성(배우자, 자녀, 직계존속, 형제자매)을 넣으면 법정 상속 순위와 비율을 계산 | 민법 상속편 (상속 순위, 배우자 가산) **[확인 필요]** |
| 유언 방식 안내 | 5가지 법적 방식별 요건, 자주 무효가 되는 지점(예: 녹음 유언에서 증인이 이름을 말하지 않음) | 민법 제1065~1070조 |
| 자필 유언 작성 도우미 | 쓸 항목 체크리스트와 예시. **손으로 직접 쓰고 날인해야 효력이 있다**는 점을 명시하고 인쇄용 양식만 제공 | 민법 제1066조 |
| 디지털 자산 정리 체크리스트 | SNS, 클라우드, 구독, 암호화폐 지갑 처리 방법과 각 서비스의 사후 계정 정책 링크 | 각 서비스 공식 안내 **[확인 필요]** |
| 사전연명의료의향서 안내 | 등록기관 찾기, 효력, 철회 방법 | 국립연명의료관리기관 **[확인 필요]** |

### 5.2 Part 3-B (서버 필요)

| 기능 | 내용 | 주의 |
|---|---|---|
| 비상 연락망 | 부고를 보낼 사람 목록 | 제3자 연락처 수집이라 본인 동의 구조가 필요하다 **[법검토]** |
| 유언 집행인(지정인) | 사후에 기록을 열람하고 부고를 발송할 권한자 | 지정인 초대와 수락, 열람 조건(사망 확인 서류 업로드 등)을 설계해야 한다 |
| 확인형 부고 발송 | 지정인이 확인하면 연락망에 부고(Part 2 빈소 페이지 링크) 발송 | 자동 판단 금지 (3절) |
| 사전 재산 목록 | 부동산, 예금, 채무 메모 | 최고 수준 민감정보. 종단간 암호화 또는 3-A처럼 기기 저장만 검토 [제안] |
| 영상·음성 메시지 | 가족에게 남기는 메시지 | "법적 유언 아님"을 표시. 녹음 유언 요건을 갖추려면 증인 구술이 필요하다는 안내 |
| 법률·세무 연계 | 무료 공공 상담처 안내, 상속세 기본 계산 | 사건별 유료 알선 금지 (3절) **[법검토]** |

## 6. Part 4 — 확장

| 기능 | 필요한 것 | 판단 |
|---|---|---|
| 디지털·기부형 화환(쌀 화환) 주문 | 통신판매업 신고, 결제(PG), 화환 업체 제휴 | 더나음이 판매자가 될지, 업체 링크만 줄지 결정 필요 |
| 현장 전광판 송출 | 장례식장 장비 연동 | 장례식장 제휴 후 |
| 행정 대행 (사망신고·상속 패키지) | 행정사 제휴. 공공 연계는 안심상속처럼 이미 정부24에 있음 | Part 1이 이미 안내 중. 대행은 광고형 연결만 (3절) |
| 영구 디지털 추모관 | 장기 보관 비용, 기일 알림 | Part 2 빈소 페이지를 "추모관 모드"로 전환하는 방식 [제안] |

## 7. 파트 사이 연결

```
Part 3 (생전)  ──장례 선호·연락망──▶  Part 2 (장례 3일)  ──종료 후──▶  Part 4 추모관
      ▲                                     │
      └──────── Part 1 장례 안내 (공공 데이터: 장례식장·화장장·장지·상조) ◀┘
```

- Part 2 빈소 페이지의 장례식장·장지 정보는 Part 1 데이터에서 고른다(직접 입력도 허용).
- Part 3 장례 선호는 임종 후 Part 1 안내와 Part 2 빈소 페이지 생성 때 기본값으로 쓴다.
- 모든 파트가 같은 도메인과 같은 디자인을 쓴다.

## 8. 진행 순서 [제안]

1. **Part 3-A**: 서버 없이 지금 구조로 바로 만들 수 있다. 법적 위험도 낮다(안내와 계산만). 1~2일.
2. **Part 2 MVP**: 백엔드를 처음 도입한다. 1차는 부고 일정, 방명록, 추모 메시지, 조의금 계좌 표시, 상주가 올린 갤러리.
3. **Part 3-B**: Part 2의 서버와 인증을 재사용한다.
4. **Part 4**: 사업자 요건(통신판매, 결제)과 제휴가 정해진 뒤.

## 9. 성공 기준 (파트별)

- **Part 2:** 조문객이 QR에서 방명록 작성까지 30초 이내. 상주가 부의록을 손으로 쓰지 않는다.
- **Part 3-A:** 사용자가 장례 선호 기록을 10분 안에 마치고 PDF로 가족에게 전달할 수 있다.
- **공통:** 법적 효력이 없는 기능을 효력이 있는 것처럼 보이게 하는 문구가 하나도 없다.

## 10. 반목표

- 시스템이 임종을 판단해 부고를 자동 발송하는 것
- 조의금이 더나음 계좌를 거치는 것
- 앱 안의 글이나 영상을 "유언장"이라고 부르는 것
- 변호사·세무사 사건 연결로 수수료를 받는 것
- 상주 동의 없이 조문객 글·사진이 공개되는 것

## 13. 사용자 결정이 필요한 것 (한 번에)

1. **Part 2 서버 비용:** 무료 구간을 넘으면 월 비용이 생긴다(예: Supabase Pro 월 25달러 수준 **[확인 필요]**). 더나음이 부담할지 정해 주세요.
2. **개인정보 처리 주체:** Part 2부터는 더나음이 개인정보처리자가 됩니다. 개인정보처리방침에 운영자(상호, 대표, 연락처)를 표시해야 합니다.
3. **현장 QR:** 빈소 QR을 HN상조 제휴 장례식장부터 시범 운영할지 정해 주세요.
4. **화환(Part 4):** 더나음이 직접 판매(통신판매업, 결제)할지, 업체 링크만 연결할지 정해 주세요.
5. **법률 검토:** 출시 전 변호사 검토(변호사법·전자금융·개인정보) 계획이 필요합니다.
